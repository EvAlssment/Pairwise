# Pairwise product parity and improvement plan

Assessment date: 20 October 2026. This compares the current Pairwise source and recorded verification against publicly documented Tuple and Hopp capabilities. A feature marked implemented in code is not automatically considered accepted on physical Macs; the hardware acceptance record remains pending.

## Product boundary

Pairwise is a macOS-first, open-source pairing client for a 10–15 person internal team, with roughly 3–4 people in a call. The product should make it easy to find a teammate, call them, share voice and optional camera video, share a display, and collaborate on the remote Mac. Keep camera opt-in; do not add call recording, cloud transcription, SSO, calendar/chat integrations, public guest access, or unattended access as part of this roadmap.

## Permission answer

Screen sharing is no longer designed around asking users to switch on the broad Screen Recording toggle. Pairwise calls Apple's native content-sharing picker and asks the user to select the display. Apple describes that explicit picker flow as allowing the selected content to be captured for that session without separate screen-capture permission. That choice and system indicator are part of macOS privacy and should remain.

Microphone and camera access are requested only after a person chooses to use them; Accessibility is requested on the Mac being shared if a teammate should control its mouse and keyboard. Apple requires the local user to authorize these. PairDesk checks Accessibility while sharing and enables control when the local user returns from System Settings; it cannot grant the permission for them. If a stale permission entry remains enabled while input fails, use the current Applications copy in System Settings, then quit and reopen that copy. Development builds may need approval again after updates because they do not have a stable Developer ID signature.

The repeat-permission problem is not fully solved for distributed builds. The source still packages an ad-hoc test build, the hardware acceptance checklist says signing is pending, and the UI warns that ad-hoc updates may need fresh approval. A stable Developer ID-signed and notarized build is the release path to validate permission persistence and prevent Gatekeeper's unsigned-app warning. This needs the team's Apple Developer identity. Until that exists, treat each ad-hoc rebuild as a new permission/installation test and avoid telling teammates that permissions are permanently fixed.

The global “Finish permission setup” warning was removed. The menu-bar now surfaces missing microphone access only during a call when the person tries to speak, and remote-control setup only while sharing. The permission window distinguishes microphone, native picker sharing, and optional host Accessibility access; it shows the current bundle path, copy location and signature, and detects other active PairDesk processes with their paths. This helps explain duplicate menu bar items and stale TCC identity without terminating another process. The UI cannot override Apple's consent or the signature identity of an ad-hoc build. Physical grant/deny/revoke and update flows remain release acceptance work.

## What we should build next

### P0 — Make macOS distribution and permission identity dependable

Produce a stable signed, notarized, stapled app and DMG from a repeatable release workflow. Verify Gatekeeper acceptance and test an in-place upgrade with existing microphone and Accessibility approvals. Publish versioned installable assets and checksums. Until signing is available, keep a clearly labeled development build and state its permission limitations.

### P1 — Close the real-Mac acceptance gap

Run the complete call with two physical Macs on current macOS: clean install, voice, screen picker, readable shared display, automatic remote control, owner takeover, Stop/Resume, emergency stop, hangup on either side, reconnection, sleep/wake, external display changes, denied/revoked permissions, and restart. Repeat with three or four participants and distant networks. Record the results in the [physical Mac acceptance record](physical-mac-acceptance.md). Fix observed failures before calling the feature complete.

### P1 — Make permission onboarding capability-based

Use three explicit states: Voice needs Microphone; Share screen opens the macOS picker; Remote control needs Accessibility on the sharing Mac. Do not make Accessibility setup a prerequisite for calling or viewing. If a grant is missing, explain what remains usable and provide a direct Settings link plus a retry check. Detect when the app is running from a disk image or a different copy and identify the app path/signature when macOS reports stale access. Do not continuously reopen settings or trap the user in an onboarding window.

### P1 — Make control state obvious and recoverable (implementation ready for hardware acceptance)

Keep who is sharing and whether control is active, waiting, paused, or unavailable visible on both Macs. Separate named cursors are implemented with distinct colors within the call; clicking a pointer temporarily uses the shared Mac's native mouse for the one action stream. Keep a one-action host stop/resume affordance visible while sharing. Preserve the safe lease/release behavior and verify held keys/buttons clear after every focus, network, app, display, and call transition. Verify drawing and laser alignment, multi-participant behavior, and latency on two physical Macs.

### P1 — Improve the shared-screen canvas

Offer display and window sources with a clear switch-source control during a call. Keep the shared content large and aspect-correct at normal and Retina sizes, allow a reliable full-screen viewer, and make control/focus state visible without covering code. Measure quality over real worldwide connections before selecting higher bitrates; use adaptive resolution/frame rate and expose a simple connection-quality indicator. In-call source switching and cancel-safe repicking are implemented; the viewer now displays measured media-path RTT with thresholds of 150 ms and 300 ms. Adaptive quality, loss/readability data, and worldwide measurements still need real network acceptance.

### P2 — Bring voice to daily-use quality

The in-call menu includes a local-only mic level meter. Device selectors and the persistent start-calls-muted preference are implemented. Reconnect state is now surfaced in the call UI; remote input is released during recovery and host control resumes only if it was enabled before reconnection. Verify recovery and device hot-plug on real Macs, add packet-loss diagnostics, and assess noise suppression if the LiveKit pipeline can provide it without harming latency. Accepting or initiating a call is the user action that enables the microphone by default; start-calls-muted leaves it off until the user unmutes. The microphone never starts at app launch.

### P2 — Finish internal operations

Administrator password reset and account enable/disable are available in the app, with session revocation and protection against disabling the last admin. `/healthz` reports process liveness and `/readyz` checks LiveKit reachability without exposing credentials. A local support report is available from Account settings; the person reviews it before copying, and raw error strings and user content are excluded. The GCP project has an enabled multi-region `/readyz` alert routed to its owner email channel; actual email delivery has not been verified. An isolated restore drill against the 20 October snapshot loaded six accounts and authenticated a throwaway user in three seconds without touching the production volume; an existing teammate's post-restore sign-in still needs owner verification. The repeatable procedure is in [production recovery](production-recovery.md). A versioned release/update path remains open. Keep SSO, external integrations, and enterprise audit features out of this phase.

## Deliberately not pursuing now

Call recording, cloud transcripts, public guest links, cross-platform clients, broad file transfer, calendar/chat integrations, SSO/SCIM, unattended remote access, and enterprise policy controls. These increase permission, privacy, operational, or support burden without improving the stated small-team pairing workflow enough to justify them yet.
