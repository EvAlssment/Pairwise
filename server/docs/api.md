# Pairdesk local backend

This service is designed for a small team. It supports self-service signup and sign-in, but does not send verification email or use an external identity provider. Signup can be disabled or restricted to email domains by the server operator. Because email ownership is not verified, only enable public signup on a team-controlled endpoint and use the domain restriction when it fits your team. Team members can change their own password in the app. Disabling an account invalidates all its sessions.

## Run locally

From `pairdesk/infra`, run `./setup.sh` and then `docker compose up --build`. The API is at `http://127.0.0.1:18080`; LiveKit websocket signaling is at `ws://127.0.0.1:17880`. All published ports bind to localhost. The named volume stores the JSON database at `/data/pairdesk.json` with mode 0600. Back up the volume as sensitive data. The JSON file uses atomic replacement and the process serializes updates with a mutex; run one API replica against a data file.

Bootstrap the first admin in the compose data volume before starting the API: from `pairdesk/infra`, run `./setup.sh`, `docker compose build api`, then `docker compose run --rm --no-deps -it --entrypoint /pairdesk-admin api create-user --admin --name 'Taylor Example' --email taylor@example.com`. The CLI prompts for a password of at least 12 characters, or reads `PAIRDESK_ADMIN_PASSWORD` if set in the environment. Deliver the initial password through an existing private channel; it is never printed. Then run `docker compose up`. Once signed in as an admin, create and manage invited members through Account settings; the CLI remains available for offline bootstrap and recovery.
## API

All endpoints use JSON. Protected routes require `Authorization: Bearer <token>`. Error responses are JSON `{ "error": "..." }`. Timestamps are UTC RFC3339. The login session is a cryptographically random opaque bearer token, stored server-side, and expires after seven days. The client should store it in Keychain and clear it on logout. Login is limited to 10 failed attempts per source IP per rolling 15 minutes per API process; a successful login clears that IP counter. Signup shares this budget and counts every attempt. Configure `PAIRDESK_SIGNUP_ENABLED=false` to disable signup and `PAIRDESK_SIGNUP_ALLOWED_DOMAINS=futurepath.ai,example.org` to restrict it to listed email domains. Domain restrictions do not verify mailbox ownership; configure email verification before using signup as proof of identity.

- `POST /v1/login` `{ "email": "...", "password": "..." }` → `{ "token": "...", "user": {"id":"...","name":"...","email":"..."}, "expiresAt":"...Z" }`
- `GET /v1/signup-policy` → `{ "enabled":true, "allowedDomains":[] }`; public client capability discovery. An empty domain list means any syntactically valid email is accepted.
- `POST /v1/signup` `{ "name":"...", "email":"...", "password":"..." }` → HTTP 201 with the same session payload as login. Creates a standard non-admin account and signs it in immediately. Password must be at least 12 characters. Duplicate email returns HTTP 409.
- `GET /v1/me` → `{ "user": {"id":"...","name":"...","email":"...","admin":true} }`; `admin` is included for administrators only.
- `POST /v1/password` `{ "currentPassword":"...", "newPassword":"..." }` → `{ "ok":true }`. New passwords must be at least 12 characters. The current session remains valid; other sessions for the account are revoked.
- `POST /v1/logout` → `{ "ok":true }`; invalidates the current session.
- `POST /v1/admin/users` (admins only) `{ "name":"...", "email":"...", "password":"..." }` → HTTP 201 `{ "user":{"id":"...","name":"...","email":"..."} }`; creates a normal invited account.
- `GET /v1/admin/users` (admins only) → all accounts and enabled state; never returns password hashes.
- `POST /v1/admin/users/{id}/password` (admins only) `{ "newPassword":"..." }` → resets the password and revokes all sessions for that account.
- `POST /v1/admin/users/{id}/enabled` (admins only) `{ "enabled":true|false }` → enables/disables an account; disabling invalidates sessions, immediately removes the member from active LiveKit rooms, and cannot disable the last enabled admin. If media removal fails, the account remains disabled and the API returns HTTP 503; retry the disable action to finish revocation.
- `GET /v1/admin/audit` (admins only) → the most recent 500 account password-reset and enable/disable actions, with actor/target IDs and timestamps only. Passwords, email addresses, tokens, and request bodies are never recorded.
- `GET /healthz` is a liveness check. `GET /readyz` checks shared storage (when configured) and the LiveKit media service and returns HTTP 503 when a dependency is unavailable; responses contain no credentials.
- `GET /v1/users` → `{ "users":[{"id":"...","name":"...","email":"...","online":true}] }`
- `POST /v1/heartbeat` `{}` → `{ "ok":true }`; marks the signed-in user online for 30 seconds.
- `POST /v1/devices` `{ "deviceId":"<stable install UUID>", "platform":"ios", "pushToken":"<standard APNs token>", "voipToken":"<optional PushKit token>" }` (or Android `{ "deviceId":"...", "platform":"android", "pushToken":"<FCM registration token>" }`) → `{ "device":{"deviceId":"...","platform":"...","updatedAt":"..."} }`; registers or replaces one device registration for the authenticated account. Push tokens are never returned. iOS requires a standard APNs token and accepts an optional VoIP token; Android accepts only its FCM `pushToken`.
- `DELETE /v1/devices/{deviceId}` → `{ "ok":true }`; removes only the authenticated account's registration for that device. Mobile clients should unregister before logging out or when their push token is invalidated, then register the refreshed token.
- `GET /v1/rooms` → `{ "rooms":[{"id":"...","name":"...","participantCount":0,"participants":[]}] }`. Participant list/count reflects active API reservations, not a LiveKit admin query.
- `GET /v1/active-calls` → `{ "calls":[{"id":"...","name":"Direct call","participantCount":2,"participants":[...]}] }`; exposes active private calls to authenticated teammates so they can request to join. Calls with fewer than two live reservations are omitted.
- `POST /v1/rooms` `{ "name":"..." }` → HTTP 201 `{ "room": {"id":"...","name":"...","participantCount":0,"participants":[]} }`
- `POST /v1/rooms/{id}/join` `{}` → `{ "room":{"id":"...","name":"...","participantCount":1}, "url":"ws://...", "token":"<LiveKit JWT>", "participantIdentity":"<stable user id>" }`
- `POST /v1/rooms/{id}/share` `{ "enabled":true|false }` → HTTP 204. One current room member can claim screen sharing; a competing claim returns HTTP 409. The server updates that connected LiveKit participant to microphone plus screen-share sources.
- `POST /v1/rooms/{id}/join-requests` `{}` → HTTP 201 `{ "request": {"id":"...","status":"pending","requester":{...},"room":{...},"expiresAt":"<RFC3339>"} }`; an online teammate can request to join an active private call. Duplicate requests to the same call are idempotent; one pending request per user is allowed and it expires after 45 seconds.
- `GET /v1/join-requests` → `{ "requests":[...] }` for the requester and active members of the relevant call. Any active call member may accept or decline; only the requester may cancel. The first acceptance reserves a room seat and authorizes that requester to join; later accept/decline attempts conflict.
- `POST /v1/join-requests/{id}/accept|decline|cancel` `{}` → `{ "request": { ... } }`. The room must still have at least two active participants at acceptance time.
- `POST /v1/rooms/{id}/leave` `{}` → `{ "ok":true }`; releases any share claim and its screen permission.
- `POST /v1/rooms/{id}/heartbeat` `{}` → `{ "ok":true }`; refreshes the room reservation. A room heartbeat before joining returns 403.
- `POST /v1/calls` `{ "userId":"<teammate id>" }` starts a private direct call; include `roomId` to invite into a room where the caller is already an active member. The target must be enabled, online, and not busy. Returns HTTP 201 `{ "call": {"id":"...","status":"pending","caller":{...},"target":{...},"room":{"id":"...","name":"Direct call","participantCount":2,"participants":[...]},"expiresAt":"<RFC3339>"} }`.
- `GET /v1/calls` → `{ "calls":[...] }` for invitations involving the signed-in user, including terminal states for 30 days and their `createdAt` timestamp. New direct-call rooms are omitted from `GET /v1/rooms`.

Call timestamps can carry up to nine fractional-second digits. New records include optional `startedAt` (when the invitation is accepted) and `endedAt` (when it reaches a terminal state). Display completed-call duration as `endedAt - startedAt`, excluding ringing time. Unanswered calls have no `startedAt`; older completed records may lack both timestamps, so clients must omit unknown durations rather than infer them from creation or expiry times. For calls accepted before an upgrade, the server preserves the previous acceptance `updatedAt` as `startedAt` when ending the call. Timeout endings reflect the server's detection of lost membership, including its reservation grace period.

- `POST /v1/calls/{id}/accept` (target only), `/decline` (target only), or `/cancel` (caller while ringing; either participant after acceptance) → `{ "call":{...} }`. Calls ring for 45 seconds. An accepted target has a 30-second room reservation to join; an expired reservation ends the invitation. Caller can join the private room while ringing; the target can join only after accepting. Leaving the room cancels pending calls from that caller and accepted calls for a departing target. A member who disappears without leaving (crash, sleep, lost network) is treated the same way once their 30-second reservation lapses: an accepted call stays active only while at least two members hold live reservations or an invitation is still ringing. The last member's next room heartbeat then returns 403, which tells the client the call ended.

When a push provider is configured, creating a direct call or join request stores one short-lived delivery job per registered device in the same atomic state-file write as the call event. An unanswered call expires after 45 seconds; the expiry worker records that outcome and queues one `missed_call` alert for the invited person's registered mobile devices. Missed-call alerts remain retryable for up to 24 hours, while call history remains available for 30 days. The worker replays pending jobs on API startup, retries transient errors with bounded backoff, drops expired or resolved events, and removes provider-invalid tokens without touching a concurrently refreshed token. Provider data contains only `event` and `callId`: `event` is `direct_call`, `join_request`, or `missed_call`; for a direct call or missed-call alert `callId` is the call invitation ID, while for a join request it is the room ID. The mobile app fetches `GET /v1/calls` or `GET /v1/join-requests` after wake to resolve the event and authenticate/authorize it. Incoming-call push remains bounded by the 45-second ring window. The production API is intentionally a single writer over its persistent data volume; do not scale it to multiple API replicas while using the JSON store. Desktop call behavior is unchanged when providers are absent or a device has no matching token.

## Media admission and limits

The backend reserves a participant slot when join succeeds. Each user has one slot per room, refreshed by the room heartbeat, and reservations expire after 30 seconds. Join refuses a fifth unexpired reservation with HTTP 409. Keep room heartbeat running while connected and call leave on exit. LiveKit JWTs last 60 seconds; they grant room join, subscribe, and microphone and data publishing only. Camera and screen-share audio are never granted. The `/share` endpoint temporarily adds screen-share video permission for the single recorded holder, and disabling or leaving removes that permission. Tokens use the stable user ID as LiveKit identity, so a user cannot appear as multiple identities.

The API creates each LiveKit room with `maxParticipants: 4`, then checks for and recreates it on every join in case LiveKit expired the idle room. Join tokens also carry `roomConfig.maxParticipants: 4` as a fallback. LiveKit applies that setting only when the room is first created; all room creation must therefore continue through this API. LiveKit is the final hard cap if API reservations temporarily disagree with connected media participants. A disconnected-but-not-left participant can occupy a LiveKit slot until LiveKit considers that participant gone, while its API reservation can expire after 30 seconds. This can cause brief false-full responses; LiveKit will not allow a fifth connected media participant. If an administrator creates a room outside this service, its capacity is not guaranteed.

## Production notes

This compose stack is development-only and binds services to localhost. Production requires HTTPS for the API and WSS for LiveKit, trusted TLS certificates, firewall rules for LiveKit signaling and UDP media, and TURN/TLS relay for restrictive networks. Keep API key/secret and session database private, rotate development values before any shared deployment, use a managed secret store, and back up encrypted persistent data. Configure reverse-proxy timeouts to allow regular heartbeat requests. The current file store and per-process login limiter are intended for one small API instance, not horizontal scaling. `LIVEKIT_API_URL` is the private admin URL (`http://livekit:7880` in compose); `LIVEKIT_URL` is the client-facing signaling URL returned by the API. No real host deployment is included.

### Mobile push setup

Push is disabled unless a complete provider configuration is present. For iOS, create an Apple Push Notification authentication key with standard and VoIP push enabled for the app's bundle ID, set `PAIRDESK_APNS_TEAM_ID`, `PAIRDESK_APNS_KEY_ID`, `PAIRDESK_APNS_TOPIC` (the app bundle ID), and `PAIRDESK_APNS_PRIVATE_KEY_FILE` (container path to the mounted `.p8` secret). Standard APNs tokens receive user-visible join-request and missed-call alerts. Only direct-call invitations use the separately registered PushKit VoIP token; the iOS app must report a VoIP push to CallKit promptly. Use Apple's sandbox APNs host for development via `PAIRDESK_APNS_HOST=https://api.sandbox.push.apple.com`; production defaults to `https://api.push.apple.com`.

For Android, create a Firebase project, enable Firebase Cloud Messaging HTTP v1, grant a service account the Firebase Cloud Messaging API Admin role, and set `PAIRDESK_FCM_PROJECT_ID` plus `PAIRDESK_FCM_SERVICE_ACCOUNT_FILE` (container path to the mounted service-account JSON secret). The server exchanges the service-account key for a short-lived OAuth access token and sends high-priority data messages with a TTL bounded by the call expiry. Do not commit `.p8` or service-account JSON files. In GCP, keep them in Secret Manager and mount them read-only into the API container; pass only secret resource references/file paths and non-secret IDs through deployment configuration. Rotate and revoke push keys through the Apple/Firebase consoles.

The current API persists device tokens, accounts, sessions, call events, and the notification outbox in the same atomically replaced JSON state file. This survives process restarts on the persistent volume and is safe for the current single API writer; it is not a multi-replica database or high-availability queue. Before increasing the API replica count or relying on push for larger deployments, migrate the state and outbox to a shared transactional database/queue. Device replacement and offboarding use the authenticated register/unregister endpoints; verify those lifecycle paths on real iOS and Android devices before a broader rollout.
